# RPK-2: Спроектировать интерфейс для удаленного управления

Сейчас проект управляется путём изменения конфигов и перезапуска сервисов. Это неудобно. 

Нужно сделать web интерфейс - максимально простой пока и утилитарный. Который сможет.

- Вычитывать конфиги из системы
- Отображать их на веб странице 
- Применять 
- Перезапускать сервисы

Нефункциональные требования

- go backend
- минимальное количество или полное отсутствие зависимостей 
- в вебе по возможности статика
- стили какой нибудь портативный бутстрап
- авторизацию пока не делаем
- https пока не поддерживаем
- статику отдает та же go-шка которая и запросы отрабатывать будет

## Решения

- Не делаем узкий сценарий (типа переключателя BM/QRA как в `bot/cmd/bot.go`) — делаем универсальный редактор: читаем оба конфига (`mmdvmhost.cfg`, `dmrgateway.cfg`) целиком, рендерим все секции/ключи как форму, сохраняем как есть.
- Код кладём в `web/` — отдельный Go-модуль по аналогии с `bot/` (свой `go.mod`, `cmd/web.go`), статика через `embed`.
- Деплой: добавляем `web.service` (systemd unit) и таргеты в `Makefile` (install/uninstall), по аналогии с mmdvmhost/dmrgateway.

## Статус

Реализовано и проверено локально (сборка + end-to-end через curl на копиях реальных конфигов из репозитория).

- `web/` — отдельный Go-модуль (`repkastar.ru/web`), единственная внешняя зависимость `gopkg.in/ini.v1` (та же, что уже использует `bot/`). Роутинг — стандартный `net/http.ServeMux` с паттернами метод+path (Go 1.22+), без сторонних роутеров.
- `web/cmd/web.go` — бинарь `repka-web`:
  - флаги `-listen` (по умолчанию `:8080`), `-mmdvmhost-config`, `-dmrgateway-config` (дефолты — реальные пути `/etc/MMDVMHost/mmdvmhost.cfg` и `/etc/DMRGateway/dmrgateway.cfg`);
  - `GET /api/configs` — читает оба ini-файла целиком, отдаёт JSON (все секции и ключи как есть, порядок сохраняется);
  - `POST /api/configs/{id}` — принимает JSON с секциями/ключами, накатывает на файл через `ini.v1` и сохраняет;
  - `POST /api/restart/{id}` — `systemctl restart <service>` (имя сервиса не приходит от клиента, а берётся из захардкоженной таблицы `configFiles` — защита от инъекции через API);
  - как и в `bot/cmd/bot.go`, явно выставлен `ini.PrettyFormat = false` — иначе `ini.v1` при сохранении выравнивает `key = value` пробелами, а кастомные парсеры `Conf.cpp` в MMDVMHost/DMRGateway это не гарантированно терпят (см. известные баги в RPK-1). Проверено diff'ом: без этого флага меняется форматирование всех строк файла, с ним — только реально изменённые значения.
- Статика (`web/cmd/static/index.html`, `app.js`, `pico.min.css`) вшита в бинарь через `go:embed` и отдаётся тем же процессом на `/`. `embed` требует, чтобы каталог `static` лежал рядом с файлом, где объявлена директива — то есть **внутри `web/cmd/`**, а не в корне модуля.
- Стили — завендоренный (не CDN) [Pico.css](https://picocss.com) v2.1.1, classless-фреймворк без сборки: минимальный CSS-файл, работает из коробки на голых `<article>/<details>/<label>` без классов. Выбран вместо настоящего Bootstrap как более лёгкий и предметный для простой формы редактирования — соответствует духу «портативный бутстрап» и «минимум зависимостей» без обращения к CDN на самом хотспоте.
- Фронтенд (`app.js`) — vanilla JS, без сборки/фреймворков: подгружает `/api/configs`, рендерит секции каждого файла в `<details>` с полями ввода, кнопки «Сохранить» и «Перезапустить» на файл.
- `web.service` — новый systemd unit, `User=root` (нужен для записи в `/etc/MMDVMHost`, `/etc/DMRGateway` и `systemctl restart`, как и у mmdvmhost/dmrgateway.service).
- `Makefile`: `deps` теперь ставит `golang-go`; добавлен файловый таргет `$(BUILD_DIR)/repka-web` (собирается из `web/cmd`), включён в `build`; `install`/`uninstall`/`services`/`restart` заведены на `repka-web`/`web.service` по аналогии с существующими бинарями.
- Собрано и протестировано локальным Go-тулчейном 1.23.4 (в системе `go`/`make` не установлены — тулчейн скачан во временную директорию только для разработки/проверки, в репозиторий не попадает). `gofmt`/`go vet` чисто. Makefile-часть не прогонялась через реальный `make` (его нет в dev-окружении) — вычитана вручную, по структуре зеркалит существующие таргеты для MMDVMHost/DMRGateway.
- Баг, найденный при проверке на реальной Repka Pi (`192.168.1.70`, Ubuntu 22.04 Jammy, `apt`-кандидат `golang-go` — только `2:1.18~0ubuntu2`): изначальная реализация роутинга использовала `net/http.ServeMux` в стиле `mux.HandleFunc("GET /api/configs", ...)` + `r.PathValue("id")` — этот синтаксис появился только в Go 1.22, на 1.18 не собирается (`go.mod` требовал `go 1.23.4`). Переписано на ручной диспатч: `mux.HandleFunc("/api/configs", ...)` / `"/api/configs/"` / `"/api/restart/"` с проверкой `r.Method` внутри хендлера и `strings.TrimPrefix(r.URL.Path, ...)` вместо `PathValue`. `go.mod` понижен до `go 1.18`. Пересобрано и повторно прогнано через тот же curl-сценарий (GET/POST, неверный метод → 405, неизвестный id → 404/500) — поведение не изменилось.

Задеплоено на реальную Repka Pi (`192.168.1.70`) через `git push` + `git pull` + `make install`; `web.service` включён и запущен (`systemctl enable --now web.service`), рестарт через веб-интерфейс проверен на реальных `mmdvmhost.service`/`dmrgateway.service` — оба ушли в `active` без разрыва работы хотспота.

По итогам первого прогона на реальном устройстве добавлено (по просьбе пользователя):
- После «Сохранить» бэкенд перечитывает файл с диска и возвращает актуальное содержимое — форма перерисовывается тем, что реально записалось, а не тем, что было отправлено.
- После «Перезапустить» бэкенд гоняет `systemctl is-active` и возвращает точный статус — виден результат, а не просто факт вызова команды.
- Статус-баннер и метка состояния сервиса стали заметными (цвет фона/текста), а не блёклым текстом.
- Вкладки сверху: «Конфиги» (форма редактирования) и «Логи» (`journalctl -u <service> -n 200 --no-pager` по каждому сервису, кнопка «Обновить» + автообновление раз в 5с, пока вкладка открыта). Новый эндпоинт `GET /api/logs/{id}?lines=N` (лимит `maxLogLines=2000`), сервис берётся из той же захардкоженной таблицы — инъекция через query исключена.
- «Лампочка» (зелёная/красная точка) у каждого конфига показывает текущее состояние сервиса: подтягивается сразу при загрузке страницы (поле `status` в `GET /api/configs`/`POST /api/configs/{id}`) и фоново обновляется раз в 5с через новый лёгкий эндпоинт `GET /api/status` (только `id`/`service`/`status`, без парсинга ini — не мешает вводу текста в незасейвленных полях).

Известные ограничения (сознательно, по нефункциональным требованиям задачи):
- Без авторизации и без HTTPS — веб-интерфейс с правами root, доступный на всех интерфейсах порта 8080 без всякой защиты. Приемлемо для текущего этапа, но перед реальным "удалённым" (не LAN) использованием стоит хотя бы поставить обратный прокси с базовой авторизацией или ограничить `-listen 127.0.0.1:8080` + SSH-туннель.
- `POST /api/configs/{id}` перезаписывает файл содержимым, присланным клиентом за один запрос — конкурентного редактирования (два открытых таба) не предусмотрено, последний сохранивший побеждает.
