# RPK-4: Нормальный инсталлятор для людей со стороны

note: описание и предназначение проекта лежит в README.md. RPK-1 уже сделал `make install` для себя (собрать, разложить бинари/конфиги-плейсхолдеры, засимлинкать systemd-юниты) — этого тикета не хватает для человека, который не читал историю репозитория.

Сейчас разворачивание хотспота предполагает: клонировать репозиторий на саму Repka Pi (или любую совместимую систему), прогнать `make install`, руками найти и заполнить плейсхолдеры (`--callsign--`, `--dmrid--`, `--freq--` и т.п.) в `mmdvmhost.cfg`/`dmrgateway.cfg`, руками завести токен/админа в `bot/config.yaml`, руками включить и стартовать сервисы. Для автора это ок, для стороннего человека — нет: нужно заранее знать про `check-config`, про то что сервисы не стартуют сами, про формат `TGRewrite0` и т.д.

Нужно сделать путь, по которому человек со своим railway/callsign/DMR ID может поставить репку с нуля без чтения `tasks/RPK-1.md` и `tasks/RPK-2.md`.

Возможные направления (выбрать по ходу работы, не все обязательны):

1. Интерактивный установщик поверх `make install` — простой скрипт/`make configure`, который спрашивает Callsign/DMR ID/частоту/BrandMeister-мастер и т.п. и сам подставляет их в конфиги вместо плейсхолдеров (вместо текстового редактирования руками).
2. Явный чеклист первого запуска в README (или вывод самого установщика) — что обязательно поменять, в каком порядке включать сервисы, как проверить что всё поднялось (BM API `last_seen`).
3. Готовый образ для SD-карты (из старого списка идей в [[Петпроджект - repka-star]]) — тяжелее в поддержке, делать только если пунктов 1-2 окажется недостаточно.

Нефункциональные требования (как в RPK-2):
- Минимум зависимостей, ничего кроме того что уже есть в Makefile/апт.
- Не ломать существующий `make install`/`make build` — новый путь дополняет, а не заменяет его.
